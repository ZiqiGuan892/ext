# Huanyu 2748 纯推理吞吐实验：TP4、TP8 与 TP8×2 对比

实验日期：2026-11-11 至 2026-11-12。原 TP4 文本/音频和 STEM 16 卡记录保留，
11 月 12 日新增原生 TP8 单副本结果；三组配置与结论统一列在[第 9 节](#9-三组结果对比与分析)。

三组聚合输出吞吐分别为 **143.520、136.173、73.921 tok/s**，按实际配置卡数均摊分别为
**35.880、17.022、4.620 tok/s/卡**。TP4 与原生 TP8 的对照保持 HTTP 并发 16；
旧 TP8×2 方案每副本并发 8，且精度参考实现等设置不同，不能把三组差异全部归因于并行拓扑。

后续分离图模式和 prefix cache 收益的实验见
[TP4 纯文本四组对照结果及方案](serve_text_graph_prefix_ablation.md)。该实验改为重复输入并重测基线：
基线聚合吞吐 139.927 tok/s，只开图模式为 470.006 tok/s（+235.89%），只开缓存为
138.619 tok/s，两者都开为 447.198 tok/s。服务端缓存命中尚未验证；这些新结果不替换
本页使用不同输入的文本/音频实测，也不与本页基线混算提升比例。

在 4 张 Ascend NPU、TP=4、单副本、eager、HTTP 并发 16、每请求输出 3072 tokens 的设置下，纯文本的聚合输出吞吐为 **143.520 tok/s**，音频输入为 **142.530 tok/s**，按 4 卡均摊分别为 **35.880** 和 **35.632 tok/s/卡**。音频吞吐低约 **0.69%**，两组在本次负载下表现接近。

音频选样共使用 65 条不同的有效波形：预检 1 条、预热 16 条、正式测量 48 条。客户端按原始 PCM 的 SHA256 去重，避免正式请求重复预检或预热的音频。成功运行的选样日志为 `Selected 65 distinct audio waveforms; skipped={}`。

短预检用于检查接口、输出数量及服务端 usage。随后完成一批预热，再依次测量三批正式请求。只有请求全部成功且报告有效，才采用正常吞吐指标。固定长度生成用于比较性能，本实验不评价回答质量。

## 3 吞吐计算方式

统计使用正式请求的服务端 `usage.completion_tokens`。设正式批次为 `b`，其中请求为 `r`：

```text
输出总量 N = sum(r.completion_tokens)
测量总时间 T = sum(b.wall_time_s)
聚合输出吞吐 = N / T
平均单卡输出吞吐 = N / T / 4
```

每批 `wall_time_s` 从提交该批第一个请求之前开始，到该批全部响应解析和校验完成为止。它包含客户端请求提交、排队、服务端音频预处理或文本 prefill、生成、网络传输及响应处理。服务端处理音频的耗时包含在请求范围内。

模型启动、客户端选样和 WAV 读取、短预检、完整预热、批次之间打印，以及最终报告写盘均不计入正式测量时间。音频文件读取、WAV 重打包和 base64 编码在客户端正式请求计时前完成。

聚合吞吐采用总输出除以总时间，不对各批次 tok/s 做简单算术平均，不把各请求延迟相加作为分母，也不使用 `1/TPOT × 并发数` 推算。并发 16 是本次负载设置，公式本身不假定任意时刻都有 16 条序列在解码。

“平均单卡吞吐”表示 TP=4 服务按四张卡均摊后的输出能力，不代表模型在单张卡上独立运行的吞吐。由于 `timing-source=none`，本次没有测量逐 token 时序，不报告 TTFT 或 TPOT。

## 4 实验结果

### 4.1 正式测量汇总

| 指标 | 纯文本 | 音频输入 |
| --- | ---: | ---: |
| HTTP 并发 | 16 | 16 |
| 每请求生成数 | 1 | 1 |
| 正式请求数 | 48 | 48 |
| 失败请求数 | 0 | 0 |
| 正式输出 tokens | 147456 | 147456 |
| 平均输入 tokens | 2048 | 81.94 |
| 正式测量总时间 s | 1027.423 | 1034.563 |
| 聚合输出吞吐 tok/s | **143.520** | **142.530** |
| 平均单卡输出吞吐 tok/s/卡 | **35.880** | **35.632** |

两份终端统计均通过报告有效性检查。纯文本原始总时间为 `1027.4231814730447 s`，原始聚合吞吐为 `143.52021898959717 tok/s`，原始平均单卡吞吐为 `35.88005474739929 tok/s/卡`。音频汇总时间和吞吐按终端打印的三位小数记录；表中与下文百分比均按展示精度取近似值。

复算如下：

```text
纯文本：147456 / 1027.4231814730447 = 143.52021898959717 tok/s
音频：  147456 / 1034.563          ≈ 142.530 tok/s

音频相对纯文本吞吐变化 ≈ (142.530 / 143.520 - 1) × 100% ≈ -0.69%
```

同样完成 147456 个输出 tokens，音频正式测量总时间增加约 **7.14 秒**，聚合吞吐减少约 **0.99 tok/s**，平均单卡减少约 **0.25 tok/s/卡**。

## 5 结论及适用范围

1. **本次固定负载下，音频与文本的端到端输出吞吐接近。** TP=4、eager、并发 16、输出 3072 tokens 时，两组平均每卡均约 35.6–35.9 tok/s；音频相对纯文本低约 0.69%。
2. **0.69% 不能当作音频编码占比。** 文本输入为 2048 tokens，音频平均输入为 81.94 tokens，输入工作量没有对齐。音频处理的额外开销可能被较短输入带来的 prefill 开销下降抵消；这是可能的解释，不是阶段耗时测量结果。本次没有单独拆分 fbank、encoder、projector、prefill 和 decode。
3. **这些数值属于并发 16 下的表现，尚不是最大吞吐。** 本次没有进行并发扫描。当前 `max_num_seqs=16` 会约束实际调度容量；仅增大客户端 HTTP 并发，增加的请求可能主要进入排队。寻找峰值需要同时考虑服务端序列容量、token 预算、KV cache 和延迟。
4. **本次结果不能量化图模式收益或训练吞吐。** 两组都使用 eager，且没有训练、评分和权重更新开销。它们适合作为后续纯推理对照基线，不能直接替代训练 step 的 `perf/throughput`。

若要隔离音频输入本身的性能影响，应进一步对齐输入 token 长度分布，并交替重复文本与音频测试。阶段归因需另做计时或 profiler 实验，采集运行与无 profiler 的吞吐结果分别记录。

### 7.2 复算与统计口径

```text
聚合输出：147456 / 1994.767 ≈ 73.921 tok/s
每副本贡献：73728 / 1994.767 ≈ 36.961 tok/s
每卡输出：147456 / 1994.767 / 16 ≈ 4.620 tok/s/卡

按方案每请求输入 2048 tokens 复算输入加输出：
(48 × 2048 + 147456) / 1994.767 / 16 ≈ 7.700 tok/s/卡
```

各副本使用同一个测量时间分母，不能将两边运行时间相加。副本贡献显示值各自四舍五入，
其和与聚合显示值可能相差 0.001 tok/s。两副本贡献相同表示各自完成了相同输出量，
并不证明其独立完成时间、逐请求延迟或设备利用率相同。

7.700 的分母仍是纯推理窗口，未包含 Actor 更新、log_prob、奖励评分或权重同步，
因此不能与训练日志的 `perf/throughput` 直接等同。4.620 是 TP8 服务按设备均摊，
不是将 35B 模型部署在单卡的实测。

### 7.3 与此前结果的关系

此前 TP4 eager 文本实验的聚合输出吞吐为 143.520 tok/s、按卡均摊为 35.880 tok/s/卡。
本次对应值约为此前的 **51.5%** 和 **12.9%**。这是两套推理配置的观察差异，
不能单独解释为增加 TP 导致的退化，也不能据此确定 HCCL 或某个算子的耗时占比。
除 TP 和副本数外，两套方案的精度参考实现、每副本并发、显存与上下文预算、采样参数也不同。

本次较低吞吐已出现在独立推理测试中，因此排查不能只关注训练更新与奖励模型开销。
后续可保留本次 TP8×2、输入、并发和容量设置，仅将 `stem_full` 与 `native`
分别测量，以区分参考实现及其附带补丁的影响。11 月 12 日已先完成原生 TP8 单副本、
并发 16 的测量，详见第 8 节；它尚不能替代同配置的单/双副本或精度对照。
图模式收益另用相同精度配置做 eager/graph 对照。
阶段或算子归因仍需独立采集，不能从这份吞吐汇总推导“通信占比 98%”。

## 9 三组结果对比与分析

### 9.1 统一结果表

这里将用户所称的 **TP8DP2** 记为 **TP8×2（外部双副本）**：两个独立的 TP8 服务，
每个 engine 自身为 DP1/PP1；不是在一个 engine 内配置 `data_parallel_size=2`。
三组都是纯推理测量，无 Actor 更新、奖励计算或训练权重同步；不与训练 step 吞吐混用。

| 指标 | TP4，单副本 | TP8，单副本 | TP8DP2，两个副本 |
| --- | ---: | ---: | ---: |
| 实测日期 | 2026-11-11 | 2026-11-12 | 2026-11-11 |
| 总卡数 | 4 | 8 | 16 |
| 每副本 / 全局 HTTP 并发 | 16 / 16 | 16 / 16 | 8 / 16（方案默认） |
| 正式请求数 | 48 | 48 | 48 |
| 正式输出 tokens | 147456 | 147456 | 147456 |
| 正式测量总时间 s | 1027.423 | 1082.858 | 1994.767 |
| 聚合输出 tok/s | **143.520** | **136.173** | **73.921** |
| 平均单卡输出 tok/s/卡 | **35.880** | **17.022** | **4.620** |
| 每副本对聚合结果的贡献 tok/s | 143.520 | 136.173 | 36.961、36.961 |
| 同输出量卡时 / TP4 卡时 | 1.000× | **2.108×** | **7.766×** |

三组均用正式输出总数除以正式墙钟时间，再除以相应设备数得到平均单卡值。
TP8DP2 的两个 36.961 采用同一共同窗口，不是分别测出的单副本独立吞吐，
两者相同也不能证明两副本的耗时或利用率相同。单卡均摊指标均不是 TP=1 实测。

### 9.2 配置差异与可比范围

| 配置 | 原生 TP4 | 原生 TP8 | 旧 TP8DP2 方案默认 |
| --- | --- | --- | --- |
| 精度路径 | 原生 serve | 原生 serve | `stem_full` 与训练 worker extension |
| 每副本 `max_num_seqs` | 16 | 16 | 8 |
| 显存预算 | 0.9 | 0.9 | 0.6 |
| 上下文上限 | 32768 | 32768 | 12288 |
| 调度 token 上限 | 16384 | 16384 | 12288，可覆盖为 16384 |
| 输入构造 | distinct，每批 16 个不同 prompt | distinct，每批 16 个不同 prompt | BS4/N4，每批 4 个 prompt 各生成 4 次 |
| 采样差异 | 客户端 temperature=1、top_p=1 | 客户端 temperature=1、top_p=1 | temperature=1、top_p=0.95、top_k=20、repetition_penalty=1.05 |
| graph / prefix cache / profiler | 关闭 | 关闭 | 关闭 |

TP4 与 TP8 的启动方案旨在只改变 TP 和设备数，其余上述关键设置对齐；
本次没有读取两份原始报告做 corpus hash、版本与最终引擎配置的完整比对。
旧 TP8DP2 的环境覆盖值仍需原 `case.json`、`launch_*.json` 和引擎日志确认，
不能把方案默认值当成全部已验证的运行事实。三组输出量相同，也不代表 prompt 内容完全相同。

### 9.3 可量化的结论

使用 TP4 和 TP8 的原始精度数值、TP8DP2 已回传的三位小数总时间复算：

| 对比 | 聚合输出吞吐变化 | 平均单卡输出吞吐变化 | 同输出量卡时倍数 |
| --- | ---: | ---: | ---: |
| 原生 TP8 相对原生 TP4 | **−5.12%** | **−52.56%** | **2.108×** |
| 旧 TP8DP2 相对原生 TP4 | **−48.49%** | **−87.12%** | **7.766×** |
| 旧 TP8DP2 相对原生 TP8 | **−45.72%** | **−72.86%** | **3.684×** |

卡时指正式测量时间乘以占用卡数；此处单位可取卡秒，比较倍数不受单位影响，
不包含服务启动、图编译或预热成本。例如：

```text
TP8 / TP4 卡时 = (1082.8581971563399 × 8) / (1027.4231814730447 × 4)
               ≈ 2.108

TP8 / TP4 平均单卡吞吐 = (136.17295448954405 / 8) / (143.52021898959717 / 4)
                       ≈ 0.4744
```

**在已声明配置下，原生 eager、并发 16 的 TP8 没有获得扩展收益。** 增加一倍卡数后，
正式时间增加约 55.435 秒（5.40%），聚合输出吞吐略降，平均单卡吞吐约为 TP4 的 47.44%。
若要保持 TP4 的平均单卡吞吐，TP8 聚合需达到约 287.040 tok/s；这只是对应目标值，
不是 TP 增加后必然达到的性能。本次没有做并发扫描，不能据此判断两种拓扑各自的峰值。

**旧 16 卡配置的低吞吐不能只用“TP8 天生慢”解释。** 原生 TP8 单副本的 136.173 tok/s
已高于旧双副本总和 73.921 tok/s。但单副本并发为 16，旧双副本各为 8，且精度、容量、
输入组织和采样不同；尚不能从两组差值计算精度补丁开销或双副本资源竞争损失。
固定全局并发 16 时，从一个副本拆成两个也改变了每个副本的 batch 工作量。

### 9.4 尚不能确认的瓶颈与后续对照

TP 增大后，每卡分到的计算变少，跨卡通信、同步等待和主机调度开销未必同步下降；
较小的计算规模也可能降低算子效率。这些都是待测的解释，本次吞吐报告没有提供各阶段占比。
尤其不能用本结果推导“正常 forward 的通信占比超过 98%”：
[之前的 profile 分析](profile_analysis_20261110.md) 中该比例来自不完整采集导出的算子时长总和，
既不等于完整 forward 墙钟占比，也不能直接套用到本次未开启 profiler 的运行。

两个独立副本的模型执行没有副本间权重同步或 forward collective，但每个 TP8 副本内部仍有
通信；同机服务还可能争用 CPU、内存带宽或设备互联资源。因此，只有在每副本配置和请求负载
一致、负载均衡且共享资源未形成瓶颈时，双副本聚合才预期接近单副本独立吞吐的两倍。
不能直接将本次并发 16 的 136.173 乘二，与旧每副本并发 8 的总吞吐比较。

以下是后续待执行的对照，不是本次已取得的结果：

1. 保持本次原生 TP8 单副本服务及容量不变，将客户端并发降为 8，测得单副本基线 `Q8`。
2. 启动两个配置相同的原生 TP8 独立服务，每副本并发 8，同时压测并用共同窗口计算 `Q2`。
   用 `Q2 / (2 × Q8)` 判断副本扩展效率；接近 1 表示接近线性扩展，显著低于 1 再查
   请求分配、共享资源竞争和长尾等待。比较需保持输入、预热和计时口径一致。
3. 固定 TP8×2、每副本并发、输入与容量，仅切换原生 / `stem_full`，分离精度参考实现的影响。
   若要评估图模式，另做同一套配置下的 eager / graph 对照。

若评估最大吞吐而非固定负载延迟，再分别扫描并发和引擎调度容量，或测量 TP4×2 等拓扑；
这些实验均须另行记录，不能以理想倍数替代实测。
